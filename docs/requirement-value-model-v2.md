# HyperOS 设计系统需求价值分级标准 v2.0（历史存档）

> 状态：**历史存档，已被 v2.1 取代**。当前标准为 [`requirement-value-model-v2.1.md`](./requirement-value-model-v2.1.md)，不要以本文档作为新评估或新代码的依据。
>
> 本文档保留不动，用于解读 `modelVersion` 为 `HyperOS Requirement Value Model v2.0` 的历史评估记录。v2.0 → v2.1 的变化见 v2.1 文档第 14 节。
>
> 相对 v1.0 的主要变化见第 13 节「版本变更说明」。

## 1. 文档目的

本标准用于评估和统计 HyperOS 设计系统相关需求的价值等级，为版本规划、资源分配和长期能力建设提供统一依据。

它需要同时覆盖两类需求：

- **当下体验问题**：用户痛点、视觉槽点、核心流程问题和舆情风险。
- **未来体系建设**：下一代硬件形态、应用框架、标准控件、Token、跨端能力和公共设计模式。

设计系统需求不能只按照“当前有多少用户投诉”判断。对于尚未完全定型的下一代产品，模型需要识别那些虽然短期需求证据不足，但能够提前建立平台基础、支撑未来复用的建设性需求。

## 2. 核心原则

### 2.1 价值单轴评估

v2.0 只评估**价值**，不评估实现成本。

- **价值分**回答“这件事为什么值得做”。
- 成本、排期、依赖、发布窗口和团队容量属于价值评估之后的**决策环节**，不进入价值分计算。

> 变化说明：v1.0 设有独立成本轴与“高成本不降价值等级”规则；v2.0 移除成本轴，成本改由评估结果之外的排期讨论承接。

### 2.2 标签不直接加分

新机、折叠屏、平板、Token、战略、专家反馈等都是分类或证据标签，不因标签本身自动增加分数。评分必须说明标签对应的实际价值因果关系。

### 2.3 先分类，再评分（分类仅用于筛选统计）

每条需求仍可选择一个主类型，但**主类型不再改变权重**。主类型与二级标签统一用于统计、筛选和分析。

> 变化说明：v1.0 用主类型选择三张不同权重表；v2.0 改为**所有需求共用一张权重表**（见第 4.2 节），主类型降级为筛选标签。

### 2.4 结果可追溯

每个维度都必须保存评分理由和证据来源。因为等级阈值和权重在 v2.0 中可调（见第 6 节、第 4.2 节），**每条评估记录必须保存当时使用的权重表和阈值配置**，否则历史统计无法复现。调整模型结构时应发布新的模型版本，不静默修改历史评估结果。

### 2.5 硬性兜底优先于打分

部分需求因法律、舆情、硬件承诺等硬性因素，价值等级已经确定，无需逐维打分。这类需求走**第 0 层直升通道**（见第 5 节），命中即定级。

## 3. 适用范围与需求类型

覆盖所有与 HyperOS 设计体验相关的需求，包括应用框架、标准控件、视觉基础、设备适配和体验优化。

每条需求选择一个主类型（**仅用于筛选和统计，不影响权重**）：

### 3.1 平台基建

包括：应用框架、标准控件、设计 Token、公共交互模式、设计规范、跨应用共享能力、设计质量治理能力。

### 3.2 适配建设

包括：新机适配、新硬件形态、折叠屏/平板/中大屏、横竖屏与窗口变化、跨设备跨端协同、新输入或输出形态。

### 3.3 体验优化

包括：单应用或跨应用体验优化、视觉风格升级、高频用户路径优化、系统槽点治理、动效/布局/信息层级优化、一致性问题修复。

建议使用的二级标签包括：

`战略承接`、`下一代能力`、`新机适配`、`折叠屏`、`平板`、`中大屏`、`跨端`、`Token`、`标准控件`、`应用框架`、`一致性`、`用户槽点`、`舆情风险`、`专家反馈`、`用户反馈`、`竞品差距`。

## 4. 价值评分模型

每个价值维度采用 0–4 五档评分：

| 分值 | 含义 |
| ---: | --- |
| 0 | 无价值或不相关 |
| 1 | 弱价值 |
| 2 | 中等价值 |
| 3 | 强价值 |
| 4 | 决定性价值 |

### 4.1 计算公式

```text
价值分 = Σ（维度评分 ÷ 4 × 对应权重）
```

价值分范围为 0–100，保留一位小数，并使用未取整分数判断等级。

### 4.2 单一权重表

所有需求共用同一张权重表，不再按主类型区分。默认权重取 v1.0 三张权重表的均值，作为“跨类型平衡型”基准：

| 价值维度 | 默认权重 |
| --- | ---: |
| 战略与未来确定性 | 23% |
| 用户问题与风险 | 17% |
| 系统影响面 | 20% |
| 体系杠杆价值 | 18% |
| 设备与生态赋能 | 12% |
| 竞争价值 | 10% |
| **合计** | **100%** |

权重可在高级设置中调整；权重合计必须为 100%，否则系统自动归一化。**每次调整权重都应记录在评估记录中，保证历史结果可复现。**

> 变化说明：相比 v1.0 三张主类型权重表，单一权重表更简单、跨需求直接可比，但失去了对“平台基建/下一代能力”类高投入长期需求的结构性保护。若统计发现基建类需求被系统性低估，可通过调整“战略与未来确定性”“体系杠杆价值”权重或第 0 层直升通道补偿。

## 5. 第 0 层 · 硬性兜底直升通道

命中以下任一条件的需求**直接定级，跳过第 6 节以外的所有维度打分**。命中直升的需求应记录命中的具体条件作为理由。

| 条件 | 直升等级 |
| --- | --- |
| 触及法律 / 政策 / 和谐社会价值观红线 | S |
| 红色（危险）/ 橙色（紧急）舆情 | S |
| 阻塞新形态设备正常使用的刚性需求 | S |
| 机型硬件卖点（已承诺发布会重点传播） | S |
| 中等（黄色）舆情 | A |

规则说明：

- 直升通道**优先于**六维打分。一条需求只要命中任一直升条件，即按对应等级定级。
- 命中多条时取**最高等级**。
- 直升需求仍需填写命中条件的证据（如舆情工单编号、发布会材料、法务意见），并标注数据来源置信度（见第 7 节）。
- 未命中任何直升条件的需求，进入第 6 节六维打分流程。

## 6. 六项价值维度的打标标准

未命中第 0 层直升通道的需求，按以下六维打分。

### 6.1 战略与未来确定性

判断需求是否承接 HyperOS 战略、下一代确定性体验或明确产品窗口。

| 分值 | 判断标准 |
| ---: | --- |
| 0 | 与产品战略、未来能力和版本目标无明显关系 |
| 1 | 符合宽泛方向，但没有明确路线、业务或产品窗口 |
| 2 | 与已提出的方向一致，未来可能需要，但时间和范围尚未确定 |
| 3 | 直接支撑已确认的版本目标、下一代产品能力或标志性体验 |
| 4 | 是实现明确战略结果或下一代标志性设计不可缺少的基础能力 |

评分理由至少应说明：对应哪项战略目标；服务哪个产品或版本窗口；缺失该能力会造成什么结果。不能仅因需求描述中出现“下一代”“战略”“高端”等词语获得高分。

### 6.2 用户问题与风险

判断问题严重度、发生频率、不满意度贡献，以及可能带来的品牌或舆情风险。

| 分值 | 判断标准 |
| ---: | --- |
| 0 | 没有明确用户问题，仅为主观偏好 |
| 1 | 个别场景或少量用户反馈，不影响核心任务 |
| 2 | 问题重复出现，对部分用户或特定场景造成明显影响 |
| 3 | 高频或高严重度问题，显著影响满意度、核心体验或品牌感知 |
| 4 | 广泛且严重地影响核心任务，或存在明确的系统级舆情风险 |

“专家认为不好”本身主要用于提高证据置信度，不等于用户价值自动升高。

### 6.3 系统影响面

判断需求覆盖范围、出现频率，以及是否影响系统的基本美学或交互面貌。

| 分值 | 判断标准 |
| ---: | --- |
| 0 | 一次性、局部、极低频场景 |
| 1 | 单应用或单组件中的边缘场景 |
| 2 | 覆盖多个页面、组件或少量应用，出现频率中等 |
| 3 | 覆盖多个系统应用、公共路径或高频界面 |
| 4 | 影响系统默认界面、核心路径或系统整体美学与交互面貌 |

业务方数量只能作为影响范围证据，不能直接等价为高分：1 个业务需求不代表必然低分；2–3 个独立业务提出相同问题，可支持中等影响判断；4 个以上业务存在共同需求，可支持较强影响判断；评分 4 仍需满足系统级、高频或默认路径条件。

### 6.4 体系杠杆价值

判断需求能否沉淀为可复用的设计系统能力，并降低未来重复建设成本。

| 分值 | 判断标准 |
| ---: | --- |
| 0 | 完全定制化，只解决当前页面问题 |
| 1 | 可形成局部规范，但复用范围有限 |
| 2 | 可被多个页面、组件或团队复用 |
| 3 | 可沉淀为 Token、标准控件、公共模式或应用框架能力 |
| 4 | 属于底层基础能力，可持续支撑大量未来需求并推动体系演进 |

“Token 先行”不是天然高价值。只有当需求能形成语义 Token、状态体系、跨组件约束，或显著减少重复设计与不一致问题时，才应获得较高分。

### 6.5 设备与生态赋能

判断需求是否支撑新机、新形态、多端体验和未来设备能力。

| 分值 | 判断标准 |
| ---: | --- |
| 0 | 与设备形态和多端体验无关 |
| 1 | 只涉及轻量尺寸或样式适配 |
| 2 | 是某类设备的必要适配，但不影响核心体验 |
| 3 | 显著影响新机、折叠屏、平板或跨端的关键体验 |
| 4 | 是已确认的新设备形态、旗舰体验或跨端能力的必要基础设施 |

“新机适配”只是标签。只有当需求决定新设备核心体验是否成立时，才应获得 3–4 分。

### 6.6 竞争价值

判断需求是在补齐关键能力缺口，还是能形成可感知、可持续的领先能力。

| 分值 | 判断标准 |
| ---: | --- |
| 0 | 与竞争能力无明显关系 |
| 1 | 友商存在类似实现，但该能力并非关键差距 |
| 2 | 可以补齐已知差距，但难以形成差异化 |
| 3 | 补齐 HyperOS 明显或独有的能力缺口，达到领先水平 |
| 4 | 能形成用户可感知、体系可复用且短期难以复制的领先基建能力 |

竞品判断必须记录对比范围、系统版本、比较日期，以及差异属于表层视觉、设计规范还是底层平台能力。

## 7. 证据与置信度（高/中/低标注）

v2.0 不再对证据做加权计算，改为对每条需求（可选：对每个维度）打**高/中/低**数据来源标注。

| 标注 | 判断标准 |
| --- | --- |
| 高 | 有正式路线、真实数据或多方验证，结论稳定 |
| 中 | 有一个明确来源、案例、数据或业务输入 |
| 低 | 主要来自推测或单个专家/需求方判断，缺少独立证据 |

> 变化说明：v1.0 用六维证据分 0–4 加权计算总体置信度；v2.0 简化为高/中/低标注，不参与算分，仅用于识别需要补充研究的需求，以及同价值需求之间的排序参考。

置信度**不改变** S/A/B/C 等级。允许出现“高价值、低置信度”的前瞻需求，避免下一代基建因早期证据不足而被系统性低估。

证据类型建议包括：产品战略或版本路线、已确认的业务需求、用户研究/满意度/行为数据、客诉/舆情/问题反馈、专家评审、竞品分析、设备规划和硬件窗口、存量设计或开发问题统计。

## 8. 价值等级（阈值可调）

系统按照价值分自动映射等级。**等级阈值可在高级设置中调整**，用于按批次校准分布。

| 等级 | 默认分数 | 价值语义 | 默认建议 |
| --- | ---: | --- | --- |
| S | ≥85 | 战略级价值 | 进入战略能力建设和版本核心候选 |
| A | 70–84.9 | 版本级价值 | 作为版本重点需求候选 |
| B | 50–69.9 | 一般价值 | 进入常规需求池，结合容量安排 |
| C | <50 | 低价值 | 暂缓、合并或重新定义问题 |

> 变化说明：v1.0 阈值固定；v2.0 允许调整阈值。**调整阈值会影响跨版本可比性**，因此每条评估记录必须保存当时使用的阈值配置。同一批需求的统计必须在同一套阈值下进行。

等级只表达需求价值，不直接等同于最终版本承诺。最终排期还需要结合成本、依赖关系、发布窗口和团队容量。

## 9. 默认排序规则

同一需求池内默认按照以下顺序排序：

1. 价值等级：`S → A → B → C`
2. 价值分：从高到低
3. 置信度：`高 → 中 → 低`
4. 提交时间：从早到晚

> 变化说明：v1.0 排序含“投入成本从低到高”一项；v2.0 移除成本轴后不再包含该项。仍不采用“价值分 ÷ 成本”的单一性价比公式，成本在价值评估之外的排期环节讨论。

## 10. 反重复计分规则

- 每条需求只能选择一个主类型。
- 标签本身不增加分数。
- 同一事实可以支撑多个维度，但每个维度必须说明不同的价值因果关系。
- 专家反馈主要提高置信度标注，不能自动提高价值分。
- 用户反馈可以同时影响用户问题评分和证据置信度，但不能在其他维度重复加分。
- 友商已有某功能，不代表 HyperOS 补齐后自动获得竞争高分。
- 多个业务提出需求，只能证明需求范围，不能直接证明战略性。
- 方案复杂、投入巨大不代表价值更高（成本不进入价值评估）。
- 已经承诺或已经投入资源不构成价值证据，避免沉没成本影响评分。

网站的数据模型至少需要支持以下字段：

模型版本固定为 `HyperOS Requirement Value Model v2.0`。未来调整权重结构或阈值机制时发布新模型版本；历史需求重新评估时生成新的评估记录，保证统计结果可追溯。

> 变化说明：相比 v1.0，字段中**移除了投入成本**、**将六项证据置信度简化为单个置信度标注**、**新增第 0 层直升命中条件**、**新增权重表配置和等级阈值配置**（因为二者在 v2.0 中可调，必须随记录保存以保证复现）。

## 12. 验收案例

正式建设网站前，使用以下案例检查模型是否符合预期：

1. **触及法律红线的需求**：命中第 0 层直升 → 直接 S，不进入六维打分。
2. **红色舆情需求**：命中第 0 层直升 → 直接 S。
3. **黄色舆情需求**：命中第 0 层直升 → 直接 A。
4. **下一代应用框架能力**：战略、影响面和体系杠杆均强 → 应进入 S 级或高 A 级。
5. **已确认的折叠屏核心体验适配**：设备赋能和战略价值高；如果只覆盖局部低频页面，不应自动进入 S 级。
6. **多个应用重复提出的标准控件**：重点检查影响面和体系杠杆；业务数量只作为范围证据。
7. **单应用局部视觉微调**：应保持 B/C 级。
8. **高频系统槽点治理**：用户问题和系统影响面高；即使战略关联较弱，也可以达到 A 级。
9. **概念性的下一代能力**：可以获得较高战略价值分；缺少路线、数据和业务确认时，应标注低置信度，但等级不因此下降。
10. **仅因友商已有而提出的跟随需求**：没有明确用户价值、系统影响或能力缺口时，竞争价值不得超过 2。

验收标准：

- 同一需求由不同评审者评分时，每个维度差异原则上不超过 1 分。
- 标签数量不得改变最终分数。
- 命中第 0 层直升的需求，等级不受六维打分影响。
- 在同一套权重和阈值配置下，相同输入必须稳定复现相同的分数和等级。
- 任意得分都能追溯到对应理由和证据。

## 13. 版本变更说明（v1.0 → v2.0）

| 变更点 | v1.0 | v2.0 | 影响 |
